# Evaluation Lenses

Use these as evidence-led lenses, not as a universal template. Verify each one against a representative discovery or change task.

- **Cold-start discoverability** — the root or an orientation artifact helps a newcomer identify the main flow and predict where a named capability lives.
- **Entry-point locality** — a reader can move from a public route, command, screen, job, or event to its owning implementation path; shared code crosses that seam only for verified shared behavior.
- **Change locality** — a small change concentrates in a coherent path instead of scattering across unrelated branches.
- **Conceptual cohesion** — code that changes together, shares language and ownership, and has the same reason to exist is easy to find together.
- **Dependency clarity** — the tree and imports reveal the direction of information and control.
- **Naming as interface** — path names communicate purpose, role, lifecycle, scope, relationships, and any deliberately encoded stable order.
- **Convention density** — one dominant placement rule is easier to learn than several local exceptions.
- **Useful depth** — each nesting level adds a meaningful distinction or reduces reconstruction work.
- **Test and documentation locality** — behavior, tests, fixtures, and orientation material follow a predictable conceptual path.

Compare capability/domain-oriented, layer/technical-role-oriented, hybrid, flat, and deeper structures only when the repository presents them as plausible alternatives. An established convention is evidence to preserve until a representative task demonstrates that it harms comprehension or locality.
